Map structured fields from agent events

In Admin → Sources & Evidence Mapping, select New mapping and KEEN Agent / OTLP logs. Choose a sample, then add field conditions. Field labels follow the JSON keys shown in the event: fields → process.name means the literal process.name key inside fields.

EvidenceCondition
All package activityAction regex ^package\.
Agent's own journal messagesfields → SYSLOG_IDENTIFIER equals keen-agent, or use fields → _SYSTEMD_UNIT equals keen-agent.service in a separate rule.
Installed packagesAction package.status and fields → package_status equals installed.
SSH session messagesfields → SYSLOG_IDENTIFIER equals the observed program, such as sshd-session. Inspect the message before choosing a more specific condition.

The outer KEEN source is keen-agent. Inside the normalised payload, source retains the configured agent input, such as system or dpkg. System identifies the registered agent. The original JSON remains your guide to available values, when configuring a rule.

Choose the operator each condition needs

Every condition pairs a field with an operator: equals, starts with, contains, does not contain, matches regex, exists or is in IP network (CIDR).

  • equals and starts with compare literal, case-sensitive text.
  • contains also compares literal, case-sensitive text; it does not interpret regular expressions.
  • does not contain matches only when the field exists, holds a non-null scalar value and lacks the text you entered. A missing field never matches, and an empty exclusion never matches anything.
  • exists checks that the key is present, regardless of its value.
  • is in IP network (CIDR) matches client addresses against a network such as 192.0.2.0/24; see Client IP evidence conditions.

Conditions join with and: every filled condition in one rule must match. Text comparisons are case-sensitive.

Write regex conditions

Matches regex searches within the selected value; it does not need to match the whole value, and comparison is case-sensitive by default. A pattern such as ^(?:gills|systemd)$ on fields → process.name matches those unit names exactly.

  • Enter the pattern without surrounding slashes.
  • Patterns follow KEEN’s shared rules: a 512-character limit, restricted constructions and bounded execution, so the editor rejects patterns that would run the matcher for too long.
  • A missing field or a non-scalar value does not match a regex condition.

Work in the focused rule editor

The editor opens as a focused view, and Back to mappings returns to the catalogue. A new rule starts with one optional row, Summary / contains:

  • Summary refers to the event’s displayed summary, so wording there is what your pattern sees.
  • A blank default Summary row adds no restriction, so rules can be driven entirely by payload conditions.
  • Conditions already saved with a regex in Summary reopen as Summary / matches regex conditions.
  • From the Summary row you can enter text, change its operator (for example to matches regex), choose another field, or remove the row.
  • More filters holds the less-used exact and regex filters.
  • A collapsed regex guide sits below the editor steps.
  • A dotted field name stays a single literal key; payload fields keep their literal JSON paths.

Preview, then save and apply to history

Use Preview to check the actual matches against collected evidence, then choose the framework targets and save.

The save confirmation disappears after a few seconds. When a historical mapping job follows save, a separate confirmation reports when that job finishes. Existing evidence keeps its current mappings until you apply a saved rule to historical evidence from the rule catalogue.

A cron invocation records a start; assess completion using a result record. Package activity supports maintenance evidence; patch SLA coverage needs a defined population, reporting period and effectiveness measure.

Map nginx request evidence

Select source KEEN Agent / OTLP logs and action http.request, then add:

  • HTTP status equals 404
  • Request path equals /.aws/config (or starts with /.aws/)
  • Log file equals /var/log/nginx/access-example.org.log.1; to include rotated and current files, use Log file starts with /var/log/nginx/access-example.org.log.

Every filled condition must match. Leave Outcome blank to include all reported outcomes.

A 404 is evidence of the HTTP response to a request; it does not by itself prove a security control prevented an attack. The agent parses standard nginx access-log timestamps and records the HTTP method. Query strings are removed from the normalized path.

Client IP evidence conditions

Nginx common/combined log records parsed by the agent include Client IP. In a mapping definition, select Client IP and equals for one address, or is in IP network (CIDR) for a network such as 192.0.2.0/24 or 2001:db8::/32. Combine with HTTP status, Request path and Log file; every condition must match. A Client IP condition matches events containing the client.ip field. IP addresses are taken from the logged remote address; nginx trusted-proxy configuration determines whether it represents the original client.
