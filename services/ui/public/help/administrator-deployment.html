Administering KEEN

Install and configure KEEN

Chapter 1 of 30

Runtime and responsibilities

KEEN uses separate workers for internal operations and HTTP collection. keen-ui serves the UI and proxies API requests; keen-api runs FastAPI. keen-worker consumes the celery queue for internal jobs such as notifications, cache refreshes and mapping backfills. keen-http-worker consumes ingest-http for built-in HTTP collectors, named HTTP connections and custom API ingester runs. keen-beat schedules work. PostgreSQL stores records; Valkey provides sessions, caches, job messaging and notifications. The optional IMAP profile adds its own worker and queue.

The ordinary and HTTP workers each default to one child process. The HTTP worker is limited to 768 MiB, one CPU and 128 PIDs. Monitor host capacity and queue age when tuning concurrency. Python application containers drop all Linux capabilities and prevent privilege escalation; no extra capability is needed for normal network connections. Keep the artifact and scheduler volumes writable by the image user, UID 10001.

Admin Ingest runners queue collection and return a task ID. A queued confirmation does not mean that collection completed. Check the appropriate worker results and logs. Inbound webhooks/agent events and interactive catalogue lookups remain API operations.

During upgrades, stop scheduling and manual submissions and let existing collection jobs on the old default queue finish. Routing changes apply to new jobs; do not purge existing jobs. Deploy matching API, worker and scheduler images and start keen-http-worker with them. Hosted demo provisioning also includes this worker.

Artefacts use the configured local storage backend or S3-compatible storage. The standard Compose configuration includes pgdata, beatdata and artifacts volumes. The API and worker must see the same artefacts. PostgreSQL contains the references, mappings and configuration needed to interpret those objects; a complete backup includes both PostgreSQL and the referenced objects.

The external HTTPS proxy forwards to the UI listener, bound to 127.0.0.1:8081 in the supplied Compose file. Do not expose PostgreSQL, Valkey or the API directly to the internet. Scrub client-supplied identity headers at the proxy. Native OIDC uses KEEN’s server-validated session cookie.

Deploy a self-managed installation

Use a supported Docker Engine and Compose plugin, DNS for the application, a trusted TLS certificate and sufficient storage for the database and artefacts. The supplied Compose file uses published KEEN images. Local builds use docker-compose.build.yml; the UI installs its pinned design-system dependency during the image build.

  1. Place the release files in the deployment directory and record the release or commit used.
  2. Create a protected .env using the release’s settings. Configure the database, Valkey, public URL, authentication and artefact backend. Use unique secrets.
  3. Configure the HTTPS proxy and firewall. Keep internal services on the private Compose network.
  4. Build the images, start the backing services, apply the migrations and start the application services.
  5. Verify HTTPS, sign-in, framework catalogues, an artefact round trip, one ingestion and a restore into a separate test environment.

Run from the keen directory. These commands apply to the supplied self-managed Compose layout.

docker compose pull
docker compose up -d postgres valkey
docker compose run --rm keen-api alembic upgrade head
docker compose up -d
docker compose ps
docker compose logs --tail=100 keen-api keen-worker keen-beat

The API startup script also applies migrations. An explicit migration step makes failures visible before the rest of an upgrade proceeds. Never run competing migration processes against the same database.

For local bootstrap, set KEEN_BOOTSTRAP_ADMIN_USERNAME and KEEN_BOOTSTRAP_ADMIN_PASSWORD before initial startup. Verify the administrator can sign in, then remove both bootstrap variables and recreate the containers. The database retains the account and its current password. Bootstrap values are not required for migrations, workers or subsequent API starts. In hosted mode, owner provisioning uses the separate hosted bootstrap and must not create a generic shared administrator.

To build from local source, use docker compose -f docker-compose.yml -f docker-compose.build.yml build before starting the backing services and applying migrations. Start the application with the same two Compose files: docker compose -f docker-compose.yml -f docker-compose.build.yml up -d.

Configure the runtime

The definitive environment schema is services/api/app/core/config.py. Most fields use the KEEN_ prefix, but some connector secrets have explicit aliases. Apply the same relevant settings to API, worker and beat. Restart or recreate affected containers after environment changes; changing a host’s .env does not change an already running container’s environment.

Core and authentication settings

KEEN_DATABASE_URL connects to PostgreSQL. KEEN_REDIS_URL connects to Valkey. KEEN_PUBLIC_BASE_URL is required: the externally reachable origin, without a path, used for links in emails and outbound messages and for browser origin checks. KEEN does not start without it. KEEN_TIMEZONE and KEEN_UI_DATE_FORMAT define installation defaults; users can have their own presentation preferences.

KEEN_LOCAL_AUTH_ENABLED controls local sign-in. KEEN_COOKIE_SECURE should remain true for production. KEEN_COOKIE_SAMESITE and KEEN_CSRF_COOKIE_SAMESITE must suit the chosen authentication flow; test the complete cross-site OIDC sign-in flow. Keep KEEN_COOKIE_DOMAIN empty for host-only cookies unless a separately reviewed deployment requires otherwise.

Native OIDC uses KEEN_OIDC_ENABLED, issuer, authorisation and token endpoints, JWKS URI, client ID, client secret, scopes and an exact redirect URI. KEEN_OIDC_TOKEN_ENDPOINT_AUTH_METHOD selects how KEEN presents its client secret to the token endpoint: client_secret_basic (the default) or client_secret_post. Configure the corresponding logout URLs where supported. Keep TLS verification and the asymmetric algorithm allowlist. Provision authorised local identities according to the selected mode; do not enable unrestricted automatic provisioning as a shortcut.

Google and GitHub integrations have their own enablement, client and claim settings. Trusted remote-user mode requires a direct peer in KEEN_SECURITY_TRUSTED_PROXY_CIDRS and a proxy that strips incoming identity headers and supplies exactly one verified identity. Keep Uvicorn proxy-header rewriting disabled, as in the supplied startup script. Do not trust a header from an internet client. Hosted mode disables local and trusted-header authentication and requires its configured owner subject and OIDC issuer.

Session settings include KEEN_SESSION_TTL_SECONDS and the session-cookie name. Login rate limiting uses the configured window and per-IP/per-username limits. Set KEEN_SECURITY_TRUSTED_PROXY_CIDRS to the addresses of the proxies in front of the API, including the supplied UI proxy. With no trusted proxy, every client shares the proxy address and per-address limits apply to the whole installation. Valkey availability is therefore security-critical as well as operationally important.

Storage, mail and privacy settings

KEEN_ARTIFACT_STORAGE_BACKEND accepts the configured backend selection; KEEN_ARTIFACT_LOCAL_DIR sets local storage. For S3, configure bucket, region, endpoint and credentials as required. KEEN_S3_USE_INSTANCE_ROLE enables the AWS credential chain in the hosted integration. Do not combine its tenant role with broad static AWS credentials.

SMTP settings include KEEN_SMTP_HOST, port, username, password, TLS or SSL mode, sender address/name and timeout. Match TLS mode to the mail service.

KEEN_EVENT_DATA_MASKING controls optional data masking. Sample PDF header/footer and evidence filename-prefix settings control export presentation. Review exported samples to confirm the intended wording and data treatment. Collect only the information needed for assurance and use automatic secret redaction as an additional safeguard.

KEEN_SCHEDULED_AUDIT_CREATE_DAYS_AHEAD controls how far ahead scheduled audits are materialised. Outbound question, reply and incident webhooks require HTTPS, validate and pin destination addresses, and follow KEEN_INGESTION_ALLOWED_CIDRS for private destinations. Loopback and link-local destinations are rejected. Signing secrets and timeouts are configurable. Store these as secrets where appropriate and test delivery without placing credentials in audit notes.

Choose the features available in KEEN

Open Administration → Features to switch workspaces and tools on or off for this installation. Only administrators can change these settings. All features start enabled. Each switch saves immediately; the status message confirms the saved change.

A parent switch controls its children. For example, turning off ISMS makes SWOT, Objectives, documents, assets and its other subsections unavailable. Turning off Risk management also turns off the Mitigator, CIA assessments, the risk register, PESTLE(E) and Interested parties. Child preferences are preserved and take effect again when the parent is enabled. The risk register uses CIA risk records and depends on that feature.

Audits, scheduled audits and sampling into audits have separate switches. Event sampling controls the PDF sampling action and adding event evidence to an audit. Questions controls asking, replying and question workspaces across KEEN. A question also follows the switch for the record it concerns: while evidence browsing is off, for example, questions about events cannot be opened, asked or answered, and they leave My Questions until evidence browsing is switched back on. Incident actions can be disabled independently.

These are availability settings for everyone, including administrators. Existing user permissions still apply when a feature is enabled. The API rejects operations belonging to disabled features. Data, relationships and audit retention protections are preserved; disabling a feature does not delete its records. Existing references and historical audit material can still appear in other enabled tools. These switches do not create confidentiality boundaries between users or erase information already downloaded.

Controls, Clauses, Sources, evidence browsing, framework visualisations and the connections explorer can also be hidden. Shared framework and reference data remains available where other enabled tools need it. Evidence collection continues when evidence browsing is off. Manage source collection separately in Sources & evidence mapping.

Account security, sign-in, administration and the administrative audit trail remain available. Scheduled audit creation and automatic effectiveness measurements pause while their features are disabled. Question notifications queued before disabling Questions are skipped when processed. A request or job already admitted can finish.

Changes take effect on subsequent API requests. Reload an open page to refresh its navigation and available controls. If another administrator changes the settings while you are editing, KEEN rejects the stale save; reload settings and try again. The configuration keeps a revision and the administrator responsible for each saved change.
