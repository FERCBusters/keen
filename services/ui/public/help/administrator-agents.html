Chapter 27 of 30

Operate Keen Agent and OTLP collectors

Keen Agent is a small service that sends signed evidence to Keen: recognised activity from server logs and, on workstations, measured security settings. Getting one running takes three steps: register it in Keen, install and enrol the agent with a single-use code, and confirm the first evidence arrives. Everything else in this chapter is detail for when you need it.

Agent identity
One registered collector. A Keen Agent proves it is that identity with its own key pair; Keen keeps only the public key.
Enrolment code
A single-use code, valid for 24 hours, that binds a new agent's key to a registered identity.
Enrollment profile
A bootstrap key that lets an autoscaling fleet register its own agents.
Evidence envelope
One Universal Evidence Utility (UEU) record: a typed, signed description of something observed or something that happened.
Evidence mode
How much of a server's log collection becomes evidence: recognised events only, events with their source lines, or every line.
Source
One log file pattern or journal selection on a server, with a parser that recognises its events.

The agent is a standalone Go service for Linux, Windows and macOS. On servers it recognises package changes, authentications, privileged commands, denied access and security alerts in selected logs. On workstations a native companion measures disk encryption, screen locking, antivirus, firewall and automatic updates. Each item becomes a UEU envelope named by an event type from an event catalogue, and Keen checks it against that catalogue, renders it and applies the existing mapping rules.

Set up agent access

  1. Open Admin → Keen Agents and select Register a collector. Choose Keen Agent (signed evidence), the device type, the key lifetime (1-365 days, default 90), the evidence mode limit and the account pseudonym type.
  2. Keen shows a single-use enrolment code once. Copy it to the machine; it expires after 24 hours or at its first use, whichever comes first.
  3. Note the endpoint. Through the standard reverse proxy it is https://keen.example.org/api/v1/otlp/logs; direct API deployments use /v1/otlp/logs. TLS must terminate at a trusted reverse proxy.

For an autoscaling fleet, create an enrollment profile instead (see below). Choose Other OTLP collector (bearer token) only for a standard OpenTelemetry collector, which cannot sign requests. Public account pseudonyms need KEEN_INTEGRATION_SECRET_KEY on the API, because Keen stores the shared pseudonym key with that encryption key.

Agents registered before Keen Agent 0.2 hold bearer tokens. They keep sending ordinary records until their tokens expire, and they cannot renew or report workstation posture. After upgrading such an agent, select Move to key on its card: its token stops working at once and Keen shows an enrolment code. In the agent's configuration, replace token_file with enrollment.code_file, install and use the code as described below, and restart the service. Keen Agent 0.1 sent every parsed line; to keep doing so, set evidence_mode: all_lines on the agent and raise its evidence mode limit here. The upgraded agent resumes from its saved log positions and sends the records 0.1 had queued as signed evidence.

Install and enrol on a Linux server

Install the signed package from the repository described at keen.cloud/agent: apt install keen-agent on Debian and Ubuntu, or dnf install keen-agent on Fedora and RHEL-compatible systems. The package creates the keen-agent service account, the configuration directory and the hardened systemd unit. Keep the configuration and the state directory during an upgrade.

  1. Edit /etc/keen-agent/config.yaml: set endpoint, enable only sources that exist on the server and choose an evidence_mode.
  2. Save the enrolment code as a single line, readable by the service only: 
    sudo install -o root -g keen-agent -m 0640 /dev/null /etc/keen-agent/enrollment-code
sudoedit /etc/keen-agent/enrollment-code
  3. Grant the service account read access to the selected logs. For journald, where the group exists: 
    sudo usermod -aG systemd-journal keen-agent
  4. Check, enrol, start and watch: 
    sudo -u keen-agent keen-agent -command check
sudo -u keen-agent keen-agent -command enroll
sudo rm /etc/keen-agent/enrollment-code
sudo systemctl enable --now keen-agent
sudo journalctl -u keen-agent -f
sudo -u keen-agent keen-agent -command status

check validates configuration, file permissions and CA loading. enroll generates the agent's Ed25519 key pair in /var/lib/keen-agent/identity.json (mode 0600), sends Keen the public key with proof that the agent holds the private key, and saves the binding Keen returns. The service also enrols on its first start if a code file is configured. status reads the latest local report while the service runs. The service reports health to Keen about once a minute.

Keep codes and identities out of arguments, YAML and shell history. The private key never leaves identity.json; back up the state directory with the same protection as other host secrets, or re-enrol a replacement machine with a new code. Avoid granting write access, CAP_AUDIT_CONTROL or CAP_DAC_READ_SEARCH; the shipped service runs without capabilities.

Going deeper: manual builds, file permissions and the systemd unit

Keen Agent is maintained in its own repository, whose release guide describes the packages for each platform and how to verify their signatures. A manual build installs the same files: build with the Go version in go.mod, create a keen-agent system account with home /var/lib/keen-agent, install the binary to /usr/bin/keen-agent, examples/config.yaml to /etc/keen-agent/config.yaml (owned by root:keen-agent, mode 0640) and packaging/keen-agent.service as the systemd unit.

For files, use a dedicated log-reader group or narrowly scoped ACLs. Auditd commonly restricts both /var/log/audit traversal and the log file itself: configure its log_group and directory permissions according to local policy, and ensure logrotate and auditd rotation create replacement files with the same read access.

The service uses /var/lib/keen-agent with mode 0700. The systemd unit limits privileges, memory, process count and writable paths; keep state_dir at its default unless you also update the unit's StateDirectory and ReadWritePaths, and test the unit against your distribution's security policy (including SELinux/AppArmor).

Workstations

On Windows and macOS, install the signed desktop package from keen.cloud/agent. Register the device in Keen as a Workstation linked to its person, then paste the enrolment code into the setup window that opens after installation. The setup helper enrols the native posture companion, saves its identity where only the system service can read it and starts it. On Linux workstations, install the server package and enable its posture collection as described in the agent repository.

Each run measures the five checks and sends one observation per measured setting and scope, followed by a coverage record listing the checks it attempted, measured and could not measure. Settings that cannot be measured are reported as unavailable; they never become evidence of a passing or failing state. Local account identifiers become pseudonymous subjects before they leave the device.

People pages show the result for each device. Keen judges the observations with versioned rules, and the result names that version. To apply your own policy, create effectiveness measures with these metric keys:

Metric keyUnitApplies to
keen.workstation.screen_lock_secondssecondsThe longest permitted idle time before the screen locks, for example lte 900.
keen.workstation.antivirus_signature_age_daysdaysThe oldest permitted antivirus signatures, for example lte 3.

With a target set, a configured screen lock or antivirus product meets the check only when its measured value satisfies the target; the observation shows both. A measure whose unit differs is ignored, and without a measure a configured protection meets the check.

Configuration and log semantics

examples/config.yaml holds the complete configuration with commented source examples. Each source names a path pattern or journal selection and a parser. Parsing is deliberately conservative: only records a parser recognises become events.

ParserRecognised events
dpkg, apt, dnfsoftware.package.changed: package installs, upgrades, removals and transactions, with versions and the requesting account as a pseudonymous subject
sysloguser.authenticated for SSH logins and failures, privileged.action.completed for sudo commands
auditdAuthentication and login records, privileged commands and denied system calls (access.denied)
ossecsecurity.alert.generated with rule, level, groups and description
raw, json, nginx, phpLines only, in all_lines mode

Each source's evidence_mode (or the global default) chooses what it sends:

ModeSends
eventsRecognised events with typed attributes. The source line is represented by its SHA-256 hash and a file offset or journal cursor.
events_with_linesRecognised events with their redacted source line included.
all_linesRecognised events with their lines, and every other line as log.line.collected.

The identity's evidence mode limit in Keen is the most it accepts. An agent learns the limit when it enrols or renews its key and sends no more than it allows; Keen also enforces the limit on receipt. Above the limit, Keen removes an event's included line and records the removal in its custody record, and keeps no log.line.collected envelopes, while still recording their place in the agent's chain.

Choose paths carefully. Source paths are restricted to /var/log, a newly discovered file starts at byte zero, and a journal source's initial read uses initial_lookback, so a broad pattern can import an unintended archive. Unknown YAML keys and unknown parsers are rejected.

Going deeper: file safety, grouping and timestamps

Configuration must be non-writable by group and others, credential files must also deny all access to others, and symlinks in any path component and non-regular files are refused. Keep log directories and configuration owned by trusted administrators.

Dpkg and legacy syslog times use the agent host's timezone. Auditd records are grouped across reads and restarts, with interleaved IDs supported; an EOE record closes a group, and groups also close after three seconds without a new record or at the size limit. Hex-encoded audit EXECVE/PROCTITLE values remain encoded.

multiline_start groups file records until the next matching line or idle/size boundary. Journald uses its native message boundaries and durable cursors; auditd grouping and multiline options apply to file sources.

Signed evidence and its checks

Every envelope follows Keen's profile of the draft UEU specification, 0.1-keen. It names its event type and the catalogue that defines it, the agent and asset that produced it, the outcome, typed facts or attributes, a pseudonymous subject where the type allows one, the privacy transformations applied at source and its place in the agent's hash chain. Its evidence hash is the SHA-256 of its RFC 8785 canonical JSON.

The agent signs a manifest listing every envelope's evidence ID and hash in each batch, and signs each HTTP request (RFC 9421 HTTP Message Signatures over the method, operation, body digest and content type). Keen checks, in order:

  1. the request signature, its time (within five minutes), its single use and that it was made for this endpoint;
  2. that each envelope is exactly its canonical form, follows the profile and, for a catalogue Keen holds, uses only that type's declared fields with their declared types and none of its prohibited fields;
  3. the batch manifest signature and that the manifest lists exactly the batch's envelopes;
  4. each envelope's place in the agent's chain.

A failure in steps 1 to 3 rejects the whole request, so nothing from it is stored. The event page shows the outcome of each check under Evidence provenance:

ResultMeaning
Signature verifiedThe batch was signed with a key Keen holds for its producer.
UnsignedThe producer sent no batch signature. The content is as received.
Signed by an unknown keyThe batch is signed with a key Keen does not hold, so the signature could not be checked.
Continuous, stream started, gap, restarted, chain broken, out of orderHow the envelope follows the previous one Keen received from the agent. A gap means envelopes in between did not arrive; the agent sends an evidence.records.discarded envelope when it discards queued evidence, which accounts for the gap.
Catalogue checked, or catalogue not heldWhether Keen validated the typed fields against the named catalogue, or only the envelope structure.
Stored as signed, or changes by KeenWhether Keen's redaction changed anything before storage, with each changed path and the reason.

Booleans, integers and timestamps cannot hold a secret, so Keen keeps typed measurements such as password_required: true whatever their names, and redacts text with its usual rules. When Keen changes an envelope, the stored copy no longer hashes to the evidence hash; its custody record keeps the original hash and lists the change. With no changes, the stored artifact is the exact signed bytes.

Each agent event's page shows the results of these checks: the batch signature, the place in the agent's chain, the catalogue validation and any changes Keen made before storage, with the evidence ID, hash, sequence and signing key. Reviewers read them there; Keen does not package evidence for offline verification.

Going deeper: catalogues

An event catalogue is the implementor's vocabulary, much as OpenID Connect leaves claim names to implementations. Keen ships its own catalogue, keen@2026.10, and accepts envelopes naming another catalogue with structural checks only. Operators can install further catalogues as JSON files in KEEN_UEU_CATALOGUE_DIR (default /app/config/ueu/catalogues); Keen loads them at start-up and refuses duplicates and catalogues that declare personal data or authentication secrets as sendable fields. Any signed-in account can list and download the catalogues Keen holds (published catalogues).

Delivery, rotation and retention

Every envelope receives a UUIDv7 evidence ID and is committed to the local queue together with its chain position and its file offset or journal cursor in one synchronised bbolt transaction. After Keen acknowledges a batch, those envelopes are removed. A crash before acknowledgement resends the same envelopes, and Keen deduplicates by identity and evidence ID while rejecting different content under the same ID.

The result is at-least-once delivery for evidence durably collected, with server-side deduplication while the events remain retained. The status file and agent card show queue bytes, record count, dropped records, chain position, source errors, key expiry and last contact; “Connected” means recent authenticated contact, so also inspect source status and queue growth.

Continuity depends on the state directory. Clearing it, or registering a new identity, starts a new chain. Never copy one agent's state to another machine: the agent refuses to run with a used chain and a missing identity. Source deletion, log rotation during a long outage, disk failure, explicit queue expiry or deleting Keen evidence can also affect these guarantees.

Going deeper: retries, pauses and queue limits
  • Network errors, 408, 429 and server errors retry with exponential backoff and jitter, honouring Retry-After up to one hour. Redirects are refused and TLS certificates and hostnames are verified; there is no insecure TLS switch.
  • Permanent client errors (including 400, 401, 403, 409, 413 and 415) pause delivery. Envelopes remain queued, collection continues until capacity, and health reports show the pause. Fix the problem and restart the service.
  • queue_mb bounds serialised queued envelopes and checkpoint bytes. At capacity, collection pauses without advancing the affected checkpoint. bbolt reuses freed pages and retains its allocated high-water size; allow disk headroom above the payload limit.
  • retention_days: 0 retains unsent envelopes indefinitely. A positive value permits removal of envelopes older than that many days since queueing; each removal is itself recorded as an evidence.records.discarded envelope with the sequence range it covers. keen-agent -command purge-queue -confirm-discard does the same for every queued envelope.
Going deeper: log rotation, archives and size limits
  • File identity uses device/inode plus a prefix fingerprint. Configure both the live filename and uncompressed rotated files. Rename rotation is supported when the rotated file remains matched. Copy-truncate is detected when its size or prefix changes and increments the gap counter.
  • Compressed archives are not replayed. Set an uncompressed retention window longer than expected outages. A missing journal cursor reports an error; resolve journal retention or start a new source name with a chosen lookback, accepting possible replay.
  • Lines over 60,000 bytes are consumed without unbounded allocation and counted as dropped. Source paths are capped at 256 matched files, each source at 32 pending groups, and retained checkpoints at 4,096.

A quiet generic OTLP collector may show no recent contact because it does not send Keen heartbeats.

Evidence and framework mapping

The server assigns source=keen-agent and binds system to the registered name. Each event's action is its event type, its outcome comes from the envelope and its actor is the pseudonymous subject, where there is one. The normalised payload holds the stored envelope under ueu, so structured-field conditions can use paths such as ueu.attributes.manager, ueu.observation.facts.encrypted or ueu.source.component.

Use Admin → Sources & evidence mapping to create rules for your own framework and controls. Useful criteria include source=keen-agent with action=software.package.changed, action=privileged.action.completed or action=access.denied, or action=user.authenticated with outcome=failure. Rules are not installed automatically for an assumed framework version, so preview them in the rule editor.

Going deeper: what agent evidence proves

A signed envelope proves which enrolled key produced it and that it is unchanged since; it cannot prove that the host told the truth, because a compromised host can sign false observations. A recorded update demonstrates an observed maintenance action; a claim about patch timeliness additionally needs asset scope, applicable requirements, deadlines and measurements. Preserve independent corroboration where required.

Security and privacy

The agent has no inbound listener, remote command channel, plugin loading, template execution or shell-based parser. Its only child processes on servers are /usr/bin/journalctl with fixed arguments and the read-only posture probes, and parsing uses bounded inputs and Go regular expressions. Install the binary, configuration, CA files and log directories under trusted ownership.

Minimisation happens at source: each event type declares the fields it may carry, and the agent drops prohibited and undeclared fields and records each removal by field name in the envelope's privacy transformations. Usernames, user IDs and Windows SIDs become HMAC-SHA256 pseudonyms. Pairwise pseudonyms use a key that never leaves the device, so the same account on two devices yields unrelated values; public pseudonyms use a key Keen issues to every agent configured for them, so the same account matches across devices. Default redaction covers common password and token assignments, bearer tokens and authentication and cookie headers; redact adds RE2 expressions, and Keen applies its own redaction and optional privacy masking again before storage.

The private spool is not encrypted by the agent; use host disk encryption if required. Keen stores no agent secret: enrolment codes and bootstrap keys are hashed, and agents hold their own private keys.

Going deeper: keys, rotation and revocation

Each request is signed once: Keen keeps each signature's nonce for ten minutes and refuses a repeat, and refuses requests while it cannot record nonces. A signature made for heartbeats cannot submit evidence or renew a key. The agent renews its key before it expires: it generates a new key pair and asks Keen, in a request signed by the current key, to bind the new public key; the old key stops working at once.

Issue enrolment code on an agent's card gives a replacement machine a new code; the current key keeps working until the code is used, then is retired. Revocation is permanent for the identity, revokes all its keys and takes effect after any already-running ingestion transaction completes; it preserves historical evidence and the verification results recorded when it was received. A key only authenticates evidence submission, heartbeats and its own renewal; it cannot read evidence, edit controls or administer Keen.

OTLP interoperability

The receiver implements the logs signal over OTLP/HTTP JSON at /v1/otlp/logs (or /api/v1/otlp/logs through the UI proxy). Keen Agent's records carry the canonical envelope as the log body, with event.name, ueu.spec_version and ueu.evidence_id attributes; the batch manifest, its signature and key ID travel as resource attributes. Other collectors registered with a bearer token can send ordinary log records, or forward UEU envelopes unchanged: forwarded batches keep their producer's signature, which Keen verifies when it holds the producer's key.

Fluent Bit's OpenTelemetry output currently sends OTLP Protobuf, which this JSON receiver cannot accept directly. An OTLP-capable intermediary must export JSON, use the Keen logs endpoint and bearer credential, and limit batches to 64 records and the receiver's byte bounds.

Ordinary log records from token collectors may carry these optional attributes:

AttributeMeaning
keen.event.idStable UUID; assigned once before queueing
keen.sourceConfigured log source name
keen.action, keen.outcome, keen.actorParsed activity
keen.summaryBounded summary
keen.field.*Additional parsed context
Going deeper: generic records and deduplication

Generic records use action=log.record, source=otlp within their normalised payload, and a deterministic UUID derived from the authenticated identity and canonical record content. This deduplicates identical retries; supply a stable keen.event.id when distinct identical records must be preserved. Keen Agent identities send UEU envelopes only.

Going deeper: receiver limits and responses

Receiver limits: 256 UEU envelopes or 64 ordinary records per request; 1 MiB compressed and decompressed body; gzip or identity encoding (a signed request's digest covers the bytes as sent); 64 KiB per envelope and 60,000 bytes per included line; 48 typed fields per envelope. Envelope times must lie between 2000 and five minutes into the future. Rate limits are 60 log requests a minute per identity and 120 rejected credentials a minute per client address, plus separate heartbeat, enrolment and renewal limits. The receiver fails closed if its rate-limit or nonce store is unavailable.

A successful response is {} after the complete batch commits. Evidence ID conflicts return 409; invalid batches return 400 with a UEU error code such as UEU_SCHEMA_VALIDATION_FAILED or UEU_EVIDENCE_VERIFICATION_FAILED; oversized requests 413; unsupported encodings 415. Server errors leave the transaction uncommitted for retry.

Check agent operation

keen-agent -command check
keen-agent -command status
systemctl status keen-agent
journalctl -u keen-agent --since "1 hour ago"

Run the checks as the agent service user so they use the same file permissions as the service. Confirm that its configuration and selected logs are readable, review queue size, source health and delivery counters, then open the agent inventory in Keen and inspect a received event: its provenance, fields, retained artefact and mapped controls.

Enrollment profiles for autoscaling fleets

When machines come and go, an enrollment profile lets each new machine register itself. Open Admin → Keen Agents → Enrollment profiles and create a profile for each cluster or environment: choose the lifetime of agent keys, the evidence mode limit and pseudonym type for its agents, an optional enrollment expiry, an optional total enrollment limit, and optional allowed client CIDRs and fleet labels. Keen shows the bootstrap key once; store it in the fleet's secret manager.

Each enrollment creates an independent agent identity bound to the machine's own key, and the agent inventory identifies its profile. Individual servers can continue using Register a collector.

Profile actionEffect
Rotate bootstrap keyReplaces the fleet's enrollment key. Enrolled agents keep their keys.
Pause enrollmentStops registrations. Existing agents can submit evidence and renew their keys. Resume permits registrations again, subject to expiry and quota.
Revoke profile and agentsPermanently disables the profile and all its agents and revokes their keys. Create a new profile for a replacement fleet; existing evidence remains.
Revoke an agentDisables that individual identity and its keys.

Profile expiry and enrollment limits apply to registration; profile revocation also applies to ingestion and renewal. Revoking a compromised fleet's bootstrap access requires revoking or rotating its key, because an attacker who retains a valid reusable key can attempt new registrations.

Configure keen-agent for an autoscaling machine

Use examples/autoscale.yaml from the agent repository as a starting point. Provision the bootstrap key from your secret manager before starting the service, at /etc/keen-agent/bootstrap-key, owned by root:keen-agent with mode 0640, and configure the agent with:

endpoint: https://keen.example.org/api/v1/otlp/logs
enrollment:
  bootstrap_key_file: /etc/keen-agent/bootstrap-key
state_dir: /var/lib/keen-agent
evidence_mode: events
sources:
  - name: system
    kind: journal
    parser: syslog

The enrollment name defaults to the hostname; an optional enrollment.name sets a stable machine name. Configure ca_file when your receiver uses a private certificate authority; HTTPS verification remains enabled. On its first start the agent generates its key pair, saves a private enrolment nonce, enrols and saves its identity atomically in /var/lib/keen-agent/identity.json with mode 0600. After enrolment the bootstrap key file can be removed from that machine.

Keep the state directory private and persistent. It must be owned by the service user with mode 0700 (the supplied systemd unit provides it). Preserve it across restarts and keep it out of reusable machine images.

Going deeper: renewal, recovery and blocked agents

The agent renews its key before it expires and recovers interrupted requests using saved private nonces. Temporary network failures and rate limits use delayed retries, and collection continues into the bounded local queue while the agent is not enrolled.

keen-agent -command status reports the profile ID, agent ID, key ID, key expiry, readiness, next retry and any blocked reason. An authentication rejection persists across restarts; resolve the cause with an administrator. For a paused profile or corrected network admission policy, stop the service, run keen-agent -command retry-credentials as the service user and restart it. Revoked or expired identities need a new enrolment code or a new profile enrolment.

Enrolment and renewal API for provisioning clients

Provisioning tools can enrol without the agent's built-in support. Over verified HTTPS, POST to /api/v1/agents/enroll with the enrolment code (kc_…) or bootstrap key (ke_…) as the Authorization bearer credential and JSON containing public_key (the raw 32-byte Ed25519 public key, unpadded base64url) created (the current time in Unix seconds), proof_nonce (32 fresh random bytes as unpadded base64url) and proof: an Ed25519 signature, unpadded base64url, over the RFC 8785 canonical JSON of {"context":"keen-agent-enroll-v2","created":…,"credential_sha256":"<hex SHA-256 of the credential>","proof_nonce":"…","public_key":"<public key>"}. Keen accepts a proof within five minutes of created and each proof nonce once, so sign a new proof for every attempt, retries included. Profile enrolment adds name and a nonce of 32 random bytes as unpadded base64url; persist the nonce privately before sending the first request.

The response names the agent, its key_id, the pseudonym type and key, the evidence mode limit and the catalogue. Retrying with the same code, or the same name, nonce and key, and a fresh proof returns the same binding; any other key is refused.

To renew, sign a POST to /api/v1/agents/renew with the current key (operation renew) carrying a new public_key, a fresh nonce and a proof by the new key over {"context":"keen-agent-renew-v1","agent_id":…,"previous_key_id":…,"public_key":…}. For 24 hours the retired key and the same nonce can recover the same response after a lost reply. The agent repository's docs/evidence-format.md specifies request signing and the envelope profile, with test vectors.

Network and secret handling

Restrict the enrolment endpoint at nginx, a load balancer or a private network, and prevent direct access around that restriction. Application-level CIDR checks use Keen's trusted-proxy configuration and ignore forwarded addresses from untrusted peers. Enrolment and renewal have fail-closed rate limits backed by Valkey, so clients should honour Retry-After and use bounded retry delays.

Fetch bootstrap keys and enrolment codes from a secret manager using the machine's workload identity where available, and keep them out of command-line arguments, images and logs. Removing a local bootstrap file does not remove copies held in user-data or provisioning logs. Use separate profiles to limit a leaked key's reach.

Agent health and journal evidence

Agent heartbeats report delivery counters, queue size, source health, the agent's chain position, each source's evidence mode and whether a source asks for more than the identity's limit allows. Review these in the agent inventory to identify collection failures or delivery backlogs, and use the agent's local status and service logs to investigate a reported problem. Heartbeats also report, per source, how many lines were filtered out and how many were read but not recognised as evidence in the chosen mode.

Journal entries are recognised by their message: SSH authentication results become user.authenticated and sudo commands privileged.action.completed, with the account as a pseudonymous subject. In all_lines mode, other entries become log.line.collected with the redacted line and their service, process, priority and host attributes. Inspect an event's structured fields when choosing mapping conditions.

Filter before agent delivery

Filtering on the host keeps noisy logs out of Keen altogether. Each source accepts include_when and exclude_when lists, and each condition has a field (a literal parsed field key), an operator and a value.

OperatorsNotes
equals, starts_with, contains, exists, in_cidrQuote numeric values such as "404". Missing fields do not match.

By default each list uses OR: a record must match any include condition if any are given, and is then discarded on any exclusion match. Set exclude_match: all under the source to require every exclude_when condition (AND); for example, client.ip in 192.0.2.0/24 AND status equals "200" discards only status 200 requests from that network. Include conditions remain OR, empty exclusion lists discard nothing, and a missing field prevents an AND exclusion.

Going deeper: what filtering changes

Redaction precedes structured filtering. Excluded records advance checkpoints but never enter the queue, and already queued events are unaffected. Status and heartbeats report persistent filtered_by_source counters for structured filters, separately from rejected records; raw regex filters are not included in those counters. Keep checkpoints when adjusting collection filters.
