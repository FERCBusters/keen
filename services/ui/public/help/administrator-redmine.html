Redmine ingestion

Redmine is a built-in, read-only REST ingester. It collects current issue snapshots and journal entries (comments and field changes), including closed issues. It uses KEEN's existing HTTPX client; no Redmine-specific library is required.

Server setup

Enable REST API in Redmine Administration → Settings → API. Create a dedicated Redmine user with access only to the projects and private notes you intend KEEN to retain, then obtain its API key from My account. The key inherits that user's permissions; KEEN performs only GET requests.

Set these in KEEN's .env and recreate the API, worker and beat containers:

KEEN_REDMINE_ENABLED=true
KEEN_REDMINE_BASE_URL=https://redmine.example.org
KEEN_REDMINE_API_KEY=YOUR_API_KEY
KEEN_REDMINE_CONFIG_PATH=/app/config/redmine.yml
KEEN_REDMINE_POLL_SECONDS=600

A path prefix such as https://example.org/redmine is supported. Credentials travel in X-Redmine-API-Key, never the URL. HTTPS and certificate verification are mandatory, redirects are rejected, requests time out and response bodies are bounded to 8 MiB. The existing KEEN ingestion network policy applies, including KEEN_INGESTION_ALLOWED_CIDRS for private networks. There is no option to disable TLS checks. Redmine collection is disabled in demo mode.

This built-in adapter has one server connection configured through the environment, like the existing GitLab adapter. Multiple project collections use that connection. The API ingester builder's encrypted connection objects are separate.

Select projects in KEEN

Open Admin → Sources & Evidence Mapping → By source → redmine → Add collection. Choose projects and enter:

  • A project identifier, such as infrastructure, or a numeric project ID; or
  • * as the sole collection to enumerate every project visible to the API user.

An optional label becomes the event's system; otherwise it is the project's identifier. The shipped project list is empty, so enabling the adapter alone does not start a broad collection. Add one or more collections, then use Ingest runners → Run Redmine, or wait for the scheduled run. A project permission failure is reported without advancing its cursor; other projects can still complete. Only one run per Redmine URL is allowed at a time.

Source-wide mapping definitions do not create collection selections by themselves. If the runner reports no projects configured, add a collection first.

Administrators can instead manage config/redmine.yml:

ui_name: Redmine
badge_color: '#B73939'
projects:
  - project: '*'
    # label: Issue management
include_journals: true
initial_lookback_days: 0
overlap_seconds: 300
max_pages: 1000
full_scan_hours: 24

Saved web-UI configuration overrides YAML. Use the UI consistently once an override exists. Shared adapter settings are editable in the source/connection management view.

initial_lookback_days: 0 fetches all existing issues on the first run. A positive number limits that initial selection to recently updated issues; all accessible journals of those issues are retained, including older comments. This initial lower bound is stored with the project cursor and retained during periodic reconciliation. Changing it later does not reset existing cursors.

Incremental scans query issues updated since the previous successful scan, with a five-minute overlap by default. A full reconciliation runs every 24 hours by default, within the recorded history window. It can detect edits to older journals even when an issue's updated timestamp was not changed. Records absent from Redmine are not deleted from KEEN. This polling adapter cannot reconstruct deleted comments or intermediate states that disappeared between polls.

Pagination reads up to 100 records per page. max_pages bounds each project-discovery or issue-list traversal; hitting the limit fails visibly and retains the cursor. Increase it (maximum 10,000) or narrow the selection for very large installations. Initial imports and reconciliation can be expensive: each issue needs a detail request, and large journals also incur artifact/deduplication work. HTTP 429 and transient failures retain the cursor and are retried on the next scheduled run. No rapid retry loop runs against Redmine.

Map Redmine evidence

Choose Create mapping, source redmine. Leave collection selection broad, or select a configured project collection. Use a real event or structured conditions to refine it.

Event actionMeaning
issue.snapshotCurrent issue state when captured
issue.commentJournal with comment text, possibly including field changes
issue.updatedJournal containing field changes without comment text

All use outcome info: closing a ticket does not automatically prove a security control succeeded. Snapshot actor is unset because the original author may not be the person who made the latest change. Journal actor identifies the journal author; edits can also expose journal.updated_by in the normalized payload.

Useful exact JSON paths include:

  • fields["project.identifier"], fields["project.id"], fields["project.name"]
  • fields["issue.id"], fields["issue.subject"]
  • fields["issue.status.name"], fields["issue.tracker.name"]
  • fields["issue.priority.name"], fields["issue.assigned_to.name"]
  • fields["issue.custom_field.12"] (actual Redmine custom-field ID)
  • fields["journal.notes"], fields["journal.private_notes"]
  • fields["change.attr.status_id.changed"] equals true
  • fields["change.attr.status_id.new_value"] equals your resolved status ID

Example: source redmine, action issue.comment, project identifier equals infrastructure, and journal notes contains patching completed. Name the mapping “Documented patch deployment and review”, then choose the appropriate patch-management controls.

For field-only journals use issue.updated. To include both comments and changes, leave action empty and require the relevant change.*.changed field. KEEN's structured fields are ANDed. Avoid assuming status IDs have identical meanings across installations.

issue.* is the issue state at capture time, including on historical journal events. The journal's details / change.* fields describe its historical change. Inspect them when mapping a historical transition. Historical comments imported in one scan may share the current issue status; that is not the status at the time each comment was written.

Events retain collection provenance and a link back to the Redmine issue/journal. They use the standard KEEN redaction, artifact storage, SHA-256 and framework-rule pipeline, including S3/immutable retention when configured for the installation. Stable content identities suppress repeated unchanged records. Edited records produce new evidence versions; earlier artifacts remain retained. Switching collection selectors does not rewrite old provenance; use structured project fields to map historical events across such a change.

Scope

This adapter covers projects for discovery and issues/journals for evidence. It does not yet collect wiki pages, time entries, news, memberships, attachment file contents or other Redmine resources. Private content is included only when returned to the configured account; existing KEEN redaction and access policies apply.
