Keen Agent protocol and persistence

The agent is a separate Go module that speaks OTLP/HTTP JSON to a receiver inside the Keen API. This chapter describes both ends of that contract and the tests that protect it.

The module is keen-agent/. Configuration is strict YAML; file readers use directory-relative, no-symlink opens and regular-file checks; journal reads call the fixed /usr/bin/journalctl binary with validated arguments; parsers have no script hooks or remote execution channel. Its Keen-specific attributes are an optional enrichment convention, so a JSON-configured Alloy or another collector can use the same receiver (the OTLP contract, limits and alternate collector configuration). Protobuf/gRPC, metrics and traces are outside this receiver's scope.

The receiver

app/agents/otlp.py validates bounded OTLP JSON and converts it into AgentEvent; generic record IDs are deterministic, a supplied keen.event.id must be a UUID, and canonicalisation makes attribute order irrelevant. app/api/routes/agents.py authenticates a scoped bearer credential, applies rate limits, reads a bounded body with a deadline, then takes the agent row lock and rechecks its credential, so revocation and ingestion serialise on that lock.

The receiver checks for an existing event identified by agent ID and event UUID: matching content is accepted idempotently and different content with the same identity is rejected. New events use store_event_with_artifact(commit=False) so the complete batch commits together, and any invalid record prevents acceptance of the batch.

Going deeper: trust boundaries, storage and digests

Agent registration is session-admin only. Only the exact log and heartbeat paths bypass browser session and CSRF handling, and their own bearer authentication is mandatory. The registered name supplies the trusted Keen event system; resource attributes remain client claims.

Each artifact persistence attempt gets a fresh object key, which supports the local write-once and hosted S3 conditional-write backends. Storage and PostgreSQL do not share a transaction, so a failed database transaction can leave an unreferenced artifact for retention-aware operational cleanup. The canonical received-record digest supports replay checks, while the artifact SHA-256 is calculated after server redaction and privacy handling and describes the stored bytes; they cover different representations, and neither proves that the originating host reported a true fact.

Test ingestion and mapping changes

Run the Go race tests and vet checks with make test in the agent module. Receiver tests in services/api/tests/test_keen_agent.py cover authentication, expiry, revocation, whole-batch rollback, duplicate and conflicting UUIDs, compression and body limits, redaction and plain-language mismatch explanations. Keep source mappings under tests in test_managed_configuration.py and test_integration_builder.py.

Before release, test your real PostgreSQL and storage backend, reverse proxy, Valkey failure behaviour and the target distribution's journal and log permissions. Exercise credential expiry, an unavailable receiver, an inode rotation and a full queue, then inspect a captured event, its retained artifact and its selected control mapping. Documentation diagrams have editable Mermaid sources under portal/docs/help-source/diagrams/; rendered SVGs ship locally with the help pages.
