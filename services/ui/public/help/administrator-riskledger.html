Risk Ledger

Risk Ledger is a pull ingester for the public alpha API. It retrieves connected suppliers, organisation risks, and individual framework controls/domains. Supplier listing uses a read-only POST search; the other operations use GET.

What the API provides

Risk Ledger dataKEEN destination
Supplier details, assessment progress, compliance summaries and propertiesJSON evidence snapshots; a vendor under People & Vendors when supplier import is enabled
RisksJSON evidence snapshots and Risk Register entries, attached to supplier-service assets
Referenced or explicitly selected controls/domainsThe Risk Ledger assessment framework, its controls and domain clauses
Assessment answers and attached evidence filesThe documented public API has no endpoints for these resources

The public API exposes control/domain lookup by UUID. It has no endpoint for enumerating every control. The imported framework is labelled imported subset; its completeness depends on discovered and configured IDs. Supplier fields such as numEvidence are counts. KEEN retains those counts as metadata.

Configure the API key

An organisation administrator generates the key in Risk Ledger Settings → API Keys. Set these values in KEEN’s environment and recreate the API, worker and beat containers:

KEEN_RISKLEDGER_ENABLED=true
KEEN_RISKLEDGER_API_KEY=your-api-key
KEEN_RISKLEDGER_POLL_SECONDS=3600
KEEN_RISKLEDGER_CONFIG_PATH=/app/config/riskledger.yml

The API key stays in the server environment and is sent as a Bearer credential. The adapter uses the fixed HTTPS origin https://api.riskledger.com/alpha, verifies TLS, rejects redirects and ignores ambient HTTP proxy settings. No credentials belong in collection JSON or YAML. Ingestion is disabled in demo mode.

Create the collection

  1. Open Sources & Evidence Mapping and its source/connection view. Select Risk Ledger and Add collection.
  2. Choose organizations. Enter * in org to use the authenticated organisation, or enter its UUID to pin the expected account. An optional label becomes the event system.
  3. Review the shared adapter settings below. Defaults import all connected suppliers and organisation risks, and discover referenced framework entries.
  4. Use Ingest runners → Run Risk Ledger. Inspect counts and errors, then review imported vendors, risks and the framework.

Each Risk Ledger connection holds one API key and its organisation input. Create a separate connection for each key. /organisations/me verifies the key’s organisation before imports begin. Select the imported framework in Admin → Frameworks if organisation framework restrictions are configured.

Scope and shared settings

Edit shared adapter settings in the source/connection view. File-managed deployments can use config/riskledger.yml before creating a web-UI override:

organizations:
  - org: '*'
    label: Supplier assurance
import_suppliers: true
import_risks: true
import_framework: true
control_ids: []
domain_ids: []
framework_level_ids: []
page_size: 100
max_pages: 100
max_run_seconds: 300
  • control_ids and domain_ids accept UUIDs already known from Risk Ledger. Risk links discover associated controls; supplier domain-compliance and framework add-on data discover domains.
  • framework_level_ids filters suppliers by riskledger → framework → level → id. Empty includes all connected suppliers. With a filter, only risks belonging to included suppliers are imported. Supplier listing is still paginated across the organisation and filtering happens locally. This selects a supplier’s Risk Ledger framework level.
  • import_suppliers controls native vendor creation. Suppliers are still read and captured when importing risks so supplier scope can be determined.
  • import_risks controls risk collection and native risk creation.
  • import_framework controls framework/domain/control retrieval and creation. Explicit ID lists apply when it is enabled.

Local records and subsequent pulls

Stable organisation/resource IDs prevent duplicate native records. Imports create missing vendors, supplier-service assets, risks, controls and domain links. Existing local fields remain as edited. Changed upstream records produce additional evidence snapshots. Absence upstream leaves local records and earlier evidence retained. A deleted local imported record will be recreated on a later enabled import.

Vendor names are never used to merge unrelated records. A name collision receives a stable Risk Ledger suffix. Risks without an available imported supplier use an organisation/supplier context asset without inventing a vendor record.

Risk Ledger scores, impact, likelihood, owner names and numeric status are retained in snapshot fields and initial risk notes. Review and assign KEEN ratings, owner and treatment state explicitly; its 5×5 scales and account identities have their own meanings. No user accounts or People entries are created from upstream names. A risk’s explicit control association creates a native risk/control link when that control is imported.

Controls use their upstream UUID as the stable reference. The title includes the domain letter and control number where supplied, and the description retains the full question and guidance. Domain clauses group related controls. Imported control text is customer-fetched content, with source links retained.

Map the evidence snapshots

Choose source riskledger. Actions are supplier.snapshot, risk.snapshot, control.snapshot and domain.snapshot; outcome is info. The event timestamp records collection time. Original modification dates remain in the JSON payload.

Use Create mapping from this event or select structured fields. Useful paths include:

  • fields → supplier.id, fields → control.id, fields → organisation.id
  • riskledger → approvalStatus, riskledger → numEvidence
  • riskledger → framework → level → id
  • riskledger → likelihood, riskledger → impact, riskledger → riskType

For example, a supplier snapshot with the expected approval state can support a supplier-review mapping. Review what that state means in your organisation. Snapshots demonstrate the information recorded in Risk Ledger at collection time; assessment-answer evidence needs the underlying answer/file access. No automatic evidence-to-control mapping is asserted from a framework definition alone.

Operation and limits

Scheduled and manual runs share a lock. Pause/resume is available with other source controls. Each run scans current API records; unchanged snapshots are deduplicated. The last successful run is recorded only after collection completes. A failed run keeps completed snapshots and reports a partial result; the next scheduled/manual run scans again.

Pages, response sizes, request timeouts and run duration are bounded. HTTP 429 or other API failures end the run without an immediate retry loop. Review the error and wait for the next scheduled run or run it manually later. For large accounts, adjust page/run limits deliberately; repeated early failures can prevent reaching later records until the underlying problem is resolved.

Standard KEEN redaction applies before persistence, including native imported text. Snapshot artefacts use the configured local/S3 storage and existing evidence-retention rules. Native vendors, assets and risks have their own lifecycle; purging events does not delete these ISMS records.
