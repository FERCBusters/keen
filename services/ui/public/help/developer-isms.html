Risk register, library and Keen Assurance Framework

Risks, documents, people, assets and SWOT items are ordinary application records with their own services, access rules and version checks. This chapter names the module that owns each one.

api/routes/risks.py handles scenarios and control links; api/routes/risk_register.py adds register views, ratings, thresholds, CSV exchange and reusable templates. Risk is the shared scenario entity: the editor, register and heatmap use the same inherent and residual likelihood and impact fields, each constrained to 1-5, with scores calculated as their product.

RiskLibraryEntry stores reusable scenario text, CIA associations, treatment guidance and suggested assessment data. Creating from a template produces a reviewable risk, and later template changes do not rewrite that assessment. Risk creation receives library_template_id; the server retrieves suggested KEEN-AF control references from the stored template, filters them against remaining controls and writes those links under KEEN-AF:1.0, even when the active framework is different.

Going deeper: migrations and CSV exchange

The release schema and seed migrations supply the risk library, unified risk and asset records, and template control mappings; earlier incremental migrations are archived in alembic/legacy_versions/. Use the active release migration chain when inspecting or extending a fresh installation.

CSV import creates new scenarios and validates the complete file before committing, with size and row limits and validation of ownership, ratings and control references. Export protects spreadsheet cells against formula interpretation. Preserve whole-file rejection and formula-safe output when changing the schema.

Documents, people and assurance records

Native documents support folders, types, tags, rich-text content, immutable content revisions, hashes and comments. The UI's update includes expected_content_version to detect concurrent content edits; preserve server-side sanitisation and version checks when extending the editor.

Keep people and accounts separate. People and personnel-assurance records are separate from login identities: a person can have no Keen account and still have a role, assets, training or other assurance records. Never turn an assurance record into an implicit authentication grant.

A vendor can supply assets, and assigning an asset to a vendor moves its single supplier relationship. ISMS objectives, measures, metrics, assets, access records and meetings link assurance activity to the framework; the access matrix records intended or assessed access while external systems enforce their own permissions. Scheduled audits and metric tasks run through the worker and need deterministic, idempotent behaviour.

SWOT domain and access boundaries

services/isms/swot.py owns SWOT validation, hierarchy edits, version checks, bounded search and relationships, and HTTP adapters retain the ISMS read/manage dependencies. IsmsSwot stores a separate context entity, IsmsSwotLink stores validated references, and the existing ISMS control and clause link tables store framework-specific mappings. A PostgreSQL transaction advisory lock serialises structural and relationship writes and expected_version rejects stale item edits.

Going deeper: target access, audits and the planning views

Related targets are resolved at read time. Risk links require the existing per-risk access predicate on both writes and reads, deleted targets are omitted, and target text and identifiers are excluded from relationship changelog entries so target permissions cannot be bypassed. Question targets use isms_swot and recheck source access through the shared question service. Audit samples use the existing source and destination permission checks; audit_swot_scope records explicit audit selection, selected titles and quadrants are deliberately shared with audit readers, scope edits require ISMS source access and existing audit ownership or admin authority, and omitting swot_ids preserves existing selections.

planning-views.js supplies shared boards, timelines, hierarchy and direct relationship visualisations using the existing local D3 asset. Labels use text nodes or the shared HTML escaping helper, status updates use protected API helpers, and drag-and-drop has a select-control alternative. New scripts remain external and use the supplied CSP. SWOT and Objective dates use ISO calendar dates, and 0010_swot_planning extends the active migration chain.
