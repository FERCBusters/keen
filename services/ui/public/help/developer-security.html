Identity, sessions and authorisation

Local authentication, supported identity-provider flows and optional trusted-header authentication resolve to application users. Normal browser sessions are stored in Valkey and referenced by an HttpOnly cookie. Active-account checks and effective permissions remain server-side decisions.

Roles are admin, normal or inherit. Inherited roles are resolved from groups; permissions combine direct and group grants. Sessions cache an authorisation snapshot and a version. Access-changing operations must bump the affected authorisation versions so later requests recompute permissions. A cache miss must not become an allow decision.

The middleware enforces namespace and write permissions, with an admin-only fallback for unrecognised writes. Domain handlers also enforce precise permissions and relationship rules. A new route needs both a deliberate middleware policy and a route-level check; hiding its button is insufficient.

OIDC uses state, nonce and PKCE, a single-use login-state record, token exchange and signature/issuer/audience/expiry validation. Identity links use issuer and subject. General deployment settings control auto-link and provisioning behaviour; do not assume every IdP mode has the same policy. Do not authorise an account simply because a supplied email looks familiar.

The dedicated-hosting integration adds security/hosted.py and bootstrap_hosted.py. Hosted mode requires the configured issuer and owner subject, restricts existing sessions to the owner and disables alternative local/header sign-in paths. Bootstrap creates or binds the owner deliberately. Tenant identity checks apply before normal OIDC user resolution and remain necessary even with an Auth0-side action.

Cookie-based writes use the CSRF cookie/header check. Hosted mode additionally checks the exact origin, including WebSocket origin checks. Webhooks use their own authentication and must remain separately protected. Preserve host-only cookies and do not broaden them to a parent domain shared by customers.

Local MFA authentication boundary

Password verification creates a five-minute, opaque pending challenge when MFA is enrolled or required. The browser receives an HttpOnly, SameSite=Strict cookie. The database stores the token hash, user, purpose, stage, credential-version snapshot, password-hash digest and expiry. This challenge never enters the application-session namespace and cannot authorise API access or WebSocket handshakes.

Factor management starts with fresh password verification and an existing factor when enrolled. All MFA POSTs enforce the configured exact Origin; browser state is kept in an HttpOnly cookie. Verification uses rate limits that fail closed when Valkey is unavailable. Database row locks serialize factor changes and recovery-code consumption per user. TOTP verification accepts a narrow clock window and rejects a previously accepted time step.

WebAuthn registration and authentication use the maintained Python webauthn verifier, checking challenge, RP ID, origin, user presence, signatures and counters. KEEN rejects cross-origin ceremonies and mismatched user handles. User verification is preferred: the local password supplies the first factor, and a security key without a biometric/PIN can supply the second. Authenticator attestation is not used to restrict hardware vendors. Local sign-in combines a password with the enrolled security key as a second factor.

Successful verification consumes the pending challenge before issuing a fresh local application session. Sessions carry the user's MFA version and verification state. Password and factor changes invalidate older local sessions at subsequent authentication checks. SSO sessions are governed separately. Account and operator changes write MFA audit entries without storing submitted codes or secrets in the audit log.

Migration 0084_local_mfa adds user MFA state, encrypted TOTP secrets, WebAuthn credentials, recovery hashes and pending challenges. The downgrade refuses while enrolled accounts exist. Tests in tests/test_local_mfa.py exercise PostgreSQL persistence, TOTP and recovery replay, origin and expiry handling, policy, session revocation and cryptographically signed WebAuthn ceremonies. Hardware/browser interoperability also belongs in deployment acceptance testing.

Security email outbox

The CI workflow uses PostgreSQL 16 and Valkey 8. Install the locked API development dependencies with poetry install --with dev --no-root in keen/services/api, and install frontend test dependencies with npm ci --prefix services/ui/tests --ignore-scripts from keen. Set KEEN_TEST_DATABASE_URL to a disposable PostgreSQL database and KEEN_REDIS_URL to the test Valkey instance, then run bash tests.sh from keen. The runner checks backend behaviour, frontend DOM workflows, JavaScript syntax and coverage, and rejects skipped backend tests.

Migration 0085_security_notifications adds a unique user/IP history and a database outbox. Successful local/native SSO session issuance records the canonical client IP using an atomic INSERT ON CONFLICT. Account mutations enqueue their change alert in the same transaction. Celery beat schedules security_notifications_task; workers claim due rows using FOR UPDATE SKIP LOCKED, record delivery or bounded retry state, and avoid logging SMTP exception messages.

MFA presentation selects a registered key by default and remembers a successful normal factor per account/browser. Verification completion automatically finishes a login; management ceremonies stay on the security settings screen. Enrolment continues to require explicit recovery-code acknowledgement. Recovery codes are never remembered as the preferred method.
